## 1. Build with the setup flow on (exact config; CONFIG_PLANT_SETUP_FLOW path)
`sdkconfig.defaults.v1` sets `CONFIG_PLANT_SETUP_FLOW=n` (the bench app). The new overlay `sdkconfig.defaults.setup` sets it to `y`; it must be listed LAST so it wins. From `projects/plant-monitor/firmware`:
```
rm -f sdkconfig
idf.py -B build-setup -D SDKCONFIG=sdkconfig.setup -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.defaults.v1;sdkconfig.defaults.setup" set-target esp32c3
idf.py -B build-setup -D SDKCONFIG=sdkconfig.setup build
grep -E '^CONFIG_PLANT_SETUP_FLOW=|^CONFIG_PLANT_BOARD_V1_SUPERMINI=|^CONFIG_BT_NIMBLE_ENABLED=' sdkconfig.setup
```
Expected: "Project build complete" and the grep shows `CONFIG_PLANT_SETUP_FLOW=y`, `CONFIG_PLANT_BOARD_V1_SUPERMINI=y`, `CONFIG_BT_NIMBLE_ENABLED=y`. **UNVERIFIED** (not run; CI builds only the default and the v1 config, both unchanged by this slice. `build-setup/` and `sdkconfig.setup` are git-ignored; still check `git status` before any commit.)

## 2. Find the unit's hw_id
Plug the unit in (USB data cable). `esptool.py -p <PORT> read_mac` prints `MAC: aa:bb:cc:dd:ee:ff`. The firmware's hw_id is `nw-` + those 12 hex digits in lower case without colons (`make_hw_id` reads the Wi-Fi STA MAC, which equals the base MAC; **UNVERIFIED**, the first boot log in step 6 shows `NW-<last 6 hex>` and must agree).

## 3. Generate the unit's secrets (PC, no hardware)
```
python3 tools/nw_sec2_gen.py gen --hw-id nw-aabbccddeeff --out ~/nilwerk-secrets/provision-out
```
Expected stdout: one line `ok hw_id=nw-aabbccddeeff verifier_fp=<8 hex> files=...` and nothing else. Two files appear, mode 0600: `<hw_id>.nvs.csv` (salt and verifier for the unit) and `<hw_id>.label.txt` (`NW1:<hw_id>:<PoP>`, the text for the label/QR).
Verify: `python3 tools/nw_sec2_gen.py check --csv <csv> --label <label>` prints `MATCH hw_id=... verifier_fp=<same 8 hex>`.
Run once per unit. The tool refuses to overwrite: if you must redo a unit, ask Nora (the old label would become invalid).

## 4. Make and flash the NVS image
```
python3 $IDF_PATH/components/nvs_flash/nvs_partition_generator/nvs_partition_gen.py generate ~/nilwerk-secrets/provision-out/<hw_id>.nvs.csv ~/nilwerk-secrets/provision-out/<hw_id>.nvs.bin 0x6000
esptool.py -p <PORT> write_flash 0x9000 ~/nilwerk-secrets/provision-out/<hw_id>.nvs.bin
idf.py -B build-setup -D SDKCONFIG=sdkconfig.setup -p <PORT> flash
```
Offset 0x9000 and size 0x6000 are the `nvs` partition of the single-app-large table that `sdkconfig.defaults` selects; confirm with `idf.py -B build-setup partition-table` before writing (**UNVERIFIED**: if it differs, use the printed values). Order matters: write NVS first, then `flash` (it does not touch the NVS partition). The write erases anything else in NVS on that unit: use fresh units only. The `.nvs.bin` is secret too; delete it when the unit is done (the CSV stays with the label).
Expected: both commands end with "Hash of data verified" / "Done". **UNVERIFIED** (the `hex2bin` CSV encoding and the generator's argument order are from memory of IDF 5.x, not run).

## 5. Print the label
Put `NW1:<hw_id>:<PoP>` (contents of the label file) on the unit as text and QR (contract: `docs/interfaces/ble-provisioning.md` section 1). Do not photograph it into any shared place.

## 6. Check on the unit (acceptance)
Monitor: `idf.py -B build-setup -D SDKCONFIG=sdkconfig.setup -p <PORT> monitor | tee setup-<hw_id>.log` (the log must not contain secrets: it shows none, check with `grep -c <first 4 chars of PoP>` before sharing). Reset the unit (cold start), then hold BOOT 3 s inside the 3 s window after the `NWSETUP press window` line (first boot enters setup without it).

| # | Check | Expected | PASS |
|---|---|---|---|
| B1 | Boot line | `NWSETUP boot: setup mode`; **no** `NWSETUP no security-2 salt/verifier in NVS` | both true |
| B2 | Advertising | a BLE scanner on a phone (e.g. nRF Connect) shows `NW-<last 6 hex of hw_id>` (UNVERIFIED) | name seen and equals the last 6 hex of the label hw_id |
| B3 | Fail closed (control unit, optional) | on a unit flashed WITHOUT step 4: `NWSETUP no security-2 salt/verifier in NVS: BLE stays off`, nothing advertised | line seen, scanner shows no `NW-` device |
| B4 | Handshake with the label PoP | with the IDF tool `esp_prov.py` (in `$IDF_PATH/tools/esp_prov`): transport ble, `--sec_ver 2`, user `wifiprov`, password = PoP from the label. Exact option names: `esp_prov.py --help` (UNVERIFIED; the tool and device agreeing on salt/verifier maths is the main open risk of this slice) | session established, the device log shows no handshake failure |
| B5 | Wrong PoP refused | repeat B4 with one character changed | handshake fails, the device counts 1 failed handshake; after 5 the log shows setup closed (FR-D07, ADR-011) |
Acceptance for 4.F2b: B1, B2, B4, B5 pass on one unit, B3 optional. B4 passing is what moves the open "wire compatibility" item from UNVERIFIED to verified; the phone app (4.A3b real BLE service) is a separate task. Record per unit: hw_id, verifier_fp, date, PASS/FAIL per row, log file name. **No PoP, salt or verifier in the record.**
If B4 fails: send the step number, `verifier_fp`, and the device log to Nora. Do not retry with other users or passwords.
