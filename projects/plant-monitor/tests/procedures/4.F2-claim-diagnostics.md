# Bench procedure: setup session events and claim diagnostics (task 4.F2, PR #215)

**STATUS: NOT RUN.** Nothing in this file has been executed on hardware. Every step is UNVERIFIED until a bench run writes the lines below into a log.
Firmware under test: the setup build at PR #215 head (the "setup flow on" CI configuration). Requirements: FR-D03 (setup ends after 5 failed handshakes or 300 s), NFR-06 (wrong PoP refused), ADR-011.

## 0. Inputs
| Input | Where it comes from |
|---|---|
| One unit built with the setup flow on, flashed from the PR #215 head | CI artifact of the firmware job, or a local `idf.py` build |
| The unit's label PoP (the code on the label) | the per-unit folder outside the repo (see `4.F2b-sec2-provisioning.md`, section 0) |
| The app (phone) with the sensor setup screen | the app build of the same release |
| Serial log of the unit | `idf.py -p <PORT> monitor \| tee setup-<hw_id>.log` |

**Secrets rule.** Do not paste the PoP into the log, the issue or a chat. Keep the wrong PoP in a shell variable only. Check the log before sharing: `grep -c -F -- "$POP" setup-<hw_id>.log` must print `0`.

## 1. Negative test: wrong proof of possession (expected to FAIL the handshake)
Expected to pass in the sense of "the logs show the refusal". A wrong PoP fails in protocomm (SRP) before any endpoint runs, so `ERR_STATE` cannot come from a wrong PoP.

1. Reset the unit. Wait for `NWSETUP boot: setup mode`.
2. In the app, start the sensor setup and enter a PoP that differs from the label in one character.
3. Watch the serial log.

| # | Expected line in the log | Pass if |
|---|---|---|
| N1 | `NWSETUP session: wrong proof of possession (failed handshakes 1)` | seen once |
| N2 | no `NWSETUP session: setup ok` | absent |
| N3 | no `NWSETUP claim in` | absent (no endpoint ran) |
| N4 | the app shows a PoP / wrong-code error, not "Linking to your account failed" (UNVERIFIED: the native library's error text was not checked; record the exact text shown) | seen |

Repeat with a wrong PoP 5 times in one setup window. Expected: the 5th failed handshake closes setup (`NWSETUP end: sleep until reset`), BLE stops advertising, and the unit does not come back until reset (FR-D03). Record the failed-handshake count on each line.

**Precondition for the 5-failure "sleep until reset" result.** The unit must have no stored record (first boot, or erased). With a stored record the glue does not sleep after a closed setup: `nw_glue_next_after_setup` returns NORMAL when a record is present (`firmware/components/provisioning/src/nw_prov_glue.c:187`, reached through `nw_glue_next_after_boot` at `:194`). Do not run the 5-failure repeat on a unit that has credentials.

## 2. Positive test: correct PoP (confirms the fix)
| # | Expected line in the log | Pass if |
|---|---|---|
| P1 | `NWSETUP session: setup ok (ADVERTISING -> SESSION)` | seen once, before any claim line |
| P2 | `NWSETUP claim in: len=<n>` then `NWSETUP claim accepted` | both seen |
| P3 | `NWSETUP wifi cred recv`, then `NWSETUP wifi cred success` (or `cred fail: reason=<n>` with a wrong Wi-Fi password) | one of the two seen after apply |
| P4 | no SSID, passphrase, token or name value in the log | `grep` for each returns 0 |

If P1 is missing, the session event did not reach the handler: stop, keep the log, and send it to the firmware owner.
