# DRAFT bench procedure: boot-loop guard and safe fallback (task 4.F7). Not a work order yet, see "Missing before this becomes a work order"

Purpose: check on a board what the host tests only prove for the decision logic (FR-D05, NFR-01, NFR-12).
NOT RUN. The ESP-IDF adapter now exists (task 4.F7b, `components/bootguard/src/nw_bootguard_idf.c`) behind `CONFIG_PLANT_BOOTGUARD`, default off, built by hand with `sdkconfig.defaults.bootguard`; CI does not compile it with the option on. The Kconfig switch for the test-only `abort()` image (step 1) does not exist yet. Every step below is UNVERIFIED. Still a DRAFT, not a work order.

Values under test: limit 5 failed boots, fallback sleep 21600 s (6 h), 12 bytes of RTC memory. The owner's acceptance of these values is recorded in the Needs Arsany sheet, not in this repo.

Known path, not changed here: a HAL init failure in `main.c` returns from `app_main` with no sleep and no confirm. The unit stays awake (no loop), and the guard counts that boot as a failed boot. Step 7 does not cover it.

## Steps
0. First flash (do this before step 1, and before any enable on a real unit). After flashing, a C3 often reports a USB, software or watchdog reset instead of power-on. The RTC magic is then garbage and the guard maps that reset reason to "other", so it answers FALLBACK (6 h sleep) on the new unit's very first boot. Open decision, not made here: either (a) flash with a full erase and a power cycle, and record the reset reason printed on the first boot, or (b) change the mapping so that a USB or software reset with garbage magic counts as first boot. Record what the board reports; until one option is chosen the guard must not be enabled on any unit.
1. Flash an image that resets on purpose before the cycle ends (a test-only `abort()` behind a Kconfig switch). Watch the serial log:
   boots 1 to 5 run (5 failed boots), the START of boot 6 prints one `NWBOOTGUARD fallback why=count ...` line and the board stops (no BLE advertising, no Wi-Fi association).
2. Fallback current (NFR-12): after the log line, 60 s mean at the battery terminal, 3.7 V, USB unplugged. Record it. Estimate to compare against: about 21.6 uA typical, 39.6 uA worst (power budget, section 12; not measured). Pass is at most 50 uA.
3. Probation: let the 6 h timer run (or shorten it in a test build). The board must run exactly one normal attempt and, with the abort still in the image, return to fallback with one more log line.
4. Confirm: flash a good image; the counter returns to 0 after one normal wake (no guard log line in 24 h).
5. Rollback: serve an OTA image that aborts on boot. The board must roll back at the start of boot 6 (after 5 failed boots), not after 8, and report the previous version on the next report.
6. RTC loss: pull the cell during a boot loop, reconnect. Record whether the counter survived (expected: no, a full power loss clears RTC memory). Record what a brownout does to RTC memory on this board (UNVERIFIED either way).

7. Unprovisioned unit: flash with no stored credentials, let the BLE setup window time out. The unit must sleep without a guard log line and must NOT fall back after 6 wakes (every sleep path calls the confirm function; adapter rule a).
8. Reset button: press reset 6 times in a row during BLE pairing. Record whether the guard falls back (depends on whether RTC memory survives a reset on this board, UNVERIFIED). Record the same for a watchdog reset.
9. Rollback failure: with no valid previous image, force a rollback. The unit must enter the long sleep (adapter rule b), not loop.
