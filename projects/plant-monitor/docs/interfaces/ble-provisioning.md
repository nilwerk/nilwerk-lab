# BLE provisioning contract (app <-> sensor), v1 DRAFT

Task 2.4 · Author: Theo · Implements ADR-011 (Proposed) amending ADR-002 · Link L-01.
Requirements: FR-D03, FR-A03, FR-D07, NFR-03, NFR-06, proposed NFR-10, FR-D09. Claim API: `openapi.yaml` (`/claim-token`, `/device-claim`).
Status: draft. **Unverified** (needs checking in 4.F2/4.A3 week 1, risk O-13): that the ESP-IDF 5.x `wifi_provisioning` security 2 and the Expo library `@orbital-systems/react-native-esp-idf-provisioning` support everything below. Fallback is security 1 (X25519 + PoP, AES-CTR) with the same endpoints.

## 1. Discovery and security
| Item | Value |
|---|---|
| Setup mode when | first boot, button press, after factory reset (FR-D07). [proposed in 4.F2, bench check needed] Button held >= 3 s = setup mode, credentials kept until a new claim succeeds; held >= 10 s = factory reset (wipes stored credentials, then setup). BLE is off in normal operation (FR-D09) |
| Advertised name | `NW-<last 6 hex of hw_id>`, e.g. `NW-d4e5f6` |
| Service UUID | `b53672dd-5227-40a0-8b6f-6f836f8a584c` (128-bit, random uuid4 generated by Mira in 4.F2; constant `NW_PROV_SERVICE_UUID` in firmware). Closes 4.A3 review C1 |
| Label / QR | text `NW1:<hw_id>:<pop>`, e.g. `NW1:nw-a1b2c3d4e5f6:7KQ2M9XD`. PoP = 8 characters of Crockford base32 (40 bits), unique per unit |
| Security | protocomm **security 2** (SRP6a with the PoP as password; device stores per-unit salt + verifier, PoP is never sent), then AES-GCM on every endpoint payload (ADR-011) |
| Guessing limit | 5 failed handshakes, or 5 minutes without completion, ends setup mode (ADR-011); button restarts it |

## 2. Endpoints (all payloads encrypted by the session)
Standard ESP endpoints keep their protobuf format (not redefined): `proto-ver`, `prov-session`, `prov-scan`, `prov-config` (SSID + passphrase, then apply).
Custom endpoints below carry UTF-8 JSON, max 2 KiB per request.

### `nw-claim` (write, then read the reply)
Request: `{"v":1,"name":"Basil on the sill","claim_token":"<from POST /claim-token>"}`
| Field | Rule |
|---|---|
| `name` | 1-80 characters, device name (UC-02) |
| `claim_token` | 22 characters base64url, single use, 15 min |
Device rules (4.F2, `nw_prov_parse_claim`): `name` counts UTF-8 characters, not bytes; control characters and invalid UTF-8 are refused; unknown scalar keys are ignored, nested values and duplicate keys are `bad_request`. `prov-config` rules: SSID 1-32 bytes, passphrase 8-63 characters or empty for an open network (4.A3 review C2).
Reply: `{"v":1,"ok":true}` or `{"v":1,"ok":false,"error":"bad_request"}`.

### `nw-hub` (write, then read the reply; optional step) - v1.1, NOT implemented in 4.F2 (A-023)
Request with a hub: `{"v":1,"host":"nilwerk-hub.local","port":8883,"ip":"192.168.1.20","ca_pem":"-----BEGIN CERTIFICATE-----...","username":"nw-a1b2c3d4e5f6","password":"<random>"}`
Request without a hub: `{"v":1,"hub":null}` (hub is needed for the local dashboard only, owner answer Q-H1).
| Field | Rule |
|---|---|
| `host`, `port` | mDNS name or DNS name; default port 8883 |
| `ip` | optional static/cached IP, tried first (ADR-012 discovery) |
| `ca_pem` | hub private CA, at most 1.5 KiB |
| `username` | must equal `hw_id` |
| `password` | 24+ random characters from the hub registrar |
Reply: `{"v":1,"ok":true}`.

### `nw-status` (read; app polls every 1 s after `prov-config` apply)
`{"v":1,"state":"<state>","reason":null}` with `state` in:
`wifi_connecting` -> `wifi_failed` (reason `auth` | `no_ap` | `timeout`) | `claiming` -> `claimed` | `claim_failed` (reason `claim_token_invalid` | `device_owned` | `network` | `server`).
Before `prov-config` apply, `nw-status` reads `{"v":1,"state":"idle","reason":null}` [added in 4.F2; the app only polls after apply, so it never sees this]. After `wifi_failed` the device forgets the failed SSID/passphrase and needs a new `prov-config` before the next apply; after `claim_failed` it forgets the used token and needs a new `nw-claim`. The 5-minute limit is not enforced while a Wi-Fi join or claim call is in flight, only before and after it.
On `claimed` the device turns BLE off, stores everything in NVS and does one hub test publish (hub result is not reported here; the app checks the hub dashboard/status).
`wifi_failed` and `claim_failed` leave setup mode open for a retry until the 5-minute limit (NFR-03: 3 minutes total budget).

## 3. Sequence (setup, FR-A03 order: find device, Wi-Fi, name, photo, plant details)
1. App: `POST /claim-token` (user signed in). If a hub is on the LAN: pair with it and obtain credential + CA (hub API, task for 4.H2).
2. User powers the sensor / presses button; app scans `NW-*`, user scans the QR (gives PoP).
3. App: security 2 handshake -> `prov-config` (SSID, passphrase) -> `nw-claim` -> `nw-hub` -> apply.
4. Sensor joins Wi-Fi, calls `POST /device-claim` (with `hw_id`, `claim_token`, `name`, `fw`), stores the returned device token.
5. App polls `nw-status` until `claimed`, then confirms via the cloud (devices row visible under RLS), then collects photo and plant details (written to `plants`, `plant_images`, `devices.plant_id` through supabase-js).

## 4. Security notes (NFR-06, NFR-10)
Wi-Fi passphrase, claim token and MQTT password exist only inside the encrypted session and then in device NVS (plaintext flash unless NVS encryption is enabled, open point Q-H6). The advertisement name is the only public identifier. The cloud never receives the Wi-Fi password.
Tests: 5.5 (iOS + Android setup, wrong PoP refused after 5 attempts), 5.9 (BLE capture shows no SSID/passphrase).
