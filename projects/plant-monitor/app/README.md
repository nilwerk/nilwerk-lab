# Plant Monitor app (tasks 4.A2 account and profile, 4.A3 device setup UI, 4.A4 slices 1 and 2 plants)

Expo (SDK 58) + TypeScript (strict). Screens: Welcome S01, Sign up / Sign in S02, Profile S03, Delete account S04, Premium sheet S40, plus (4.A4 slice 1) Plant list S20, Plant detail S21 (with hourly table S22 and metadata), Photo gallery S23, Remove plant S24b/S24c with export first, a Plants/Profile tab bar
(wireframes: `wireframes/index.html`). Requirements: FR-A01 (account), FR-P04 (plan mirrors `profiles.is_premium`), NFR-06 (own rows only, RLS), NFR-07 (delete removes all data, export first).
Brand: the aligned set approved in A-040 (`theme.ts`, `tokens.json`, `assets/` copied from `showcase/brand/app/`; regenerate there, not here). English only, strings in `strings/en.json` (A-024).

## Run
```bash
npm ci
npm run typecheck && npm test                      # typecheck + 261 unit/screen tests (no backend needed)
EXPO_PUBLIC_MOCK_AUTH=1 npx expo start --web       # whole app against an in-memory mock of Supabase (no account, no network)
```
Real backend (needs a Supabase project, Arsany's step, see `../cloud/README.md`): set these environment variables before `expo start` / EAS build. Names only, values are never committed:

| Name | What |
|---|---|
| `SUPABASE_URL` | project URL (https) |
| `SUPABASE_PUBLISHABLE_KEY` | the NEW publishable key (`sb_publishable_...`), public by design; never a secret / service-role key |
| `CONTACT_EMAIL` | address behind "Contact us" on the Premium sheet. Default `nilwerk.team@gmail.com` (A-048, the one shared mailbox for now); set another value to override, set it to an empty string to hide the link. Opens `mailto:` with subject "Plant Monitor – Premium activation" |

`app.config.ts` copies them into `extra`; `src/config.ts` reads them. Without them the app shows a "not connected to a server" message instead of crashing.

## Device setup flow (4.A3 UI + 4.A3b slice 1 real BLE code, no hardware run)
Profile -> "Add a sensor" -> S10 find sensor, S11 connect (type the label code), S12 Wi-Fi, S13 name and link (+ S13e error states), S14 photo, S15 plant details, S16 done with the setup timer (target 3 min, NFR-03). Requirements: FR-A03, FR-D03, FR-A04, FR-A05, FR-A02 (add another). **No hub pairing step: the Raspberry Pi hub and screen S17 are v1.1, not v1 (A-023).** Plant removal / release (A-022) is separate.
- The screens only talk to `src/provisioning/types.ts` (`ProvisioningService`, `PlantSetupService`, `PhotoSource`), mirroring `docs/interfaces/ble-provisioning.md` and `openapi.yaml` (`/claim-token`, `/device-claim`). `fakeProvisioning.ts` implements it in memory (5 wrong codes close setup mode, wifi_failed / device_owned / claim failures) and runs the whole flow in tests and in the mock web build (`EXPO_PUBLIC_MOCK_AUTH=1`). Pure state machine: `src/screens/setup/setupState.ts`.
- **4.A3b slice 1 (real BLE, built, NOT run on any hardware):** `src/provisioning/bleProvisioning.ts` implements `ProvisioningService` for real: scan for `NW-xxxxxx` (name prefix + service UUID `b53672dd-5227-40a0-8b6f-6f836f8a584c` where the platform reports it), security-2 connect with the label secret, Wi-Fi scan, `POST /claim-token` -> `nw-claim` -> prov-config/apply -> follow `nw-status` (1 s) -> confirm the devices row under RLS, and maps every outcome to the existing setup error states (the 5-wrong-secrets cut-off is the device's: the app only reports `wrong_code`, or `setup_closed` once the sensor stops advertising). All Bluetooth goes through `bleAdapter.ts`; `espAdapter.ts` is the glue to `@orbital-systems/react-native-esp-idf-provisioning` **0.7.1** (exact pin, loaded lazily); `claimApi.ts` is the cloud side. `App.tsx` uses it when the build is not mock, Supabase is configured and the platform is not web; otherwise the mock or "not available" path is unchanged. Tests (mocked adapter / library / fetch, with error paths) are in `src/__tests__/bleProvisioning.test.ts` and `espAdapter.test.ts`.
- **Dev build (needed for BLE, Expo Go cannot do it):** `package.json` has `expo-dev-client` (~58.0.21, the version `expo install` picks for SDK 58) and the BLE library; `app.config.ts` has both config plugins (BLE only, `neverForLocation`). `npx expo prebuild --no-install` was run on a scratch copy and produced the expected Android permissions (BLUETOOTH_SCAN with neverForLocation, BLUETOOTH_CONNECT, location capped at API 30) and iOS `NSBluetoothAlwaysUsageDescription`. **Not run:** the native compile (`expo run:android` / EAS), because no Android SDK / Xcode / EAS account here. **UNVERIFIED:** the library's peer dependencies are `expo/react/react-native: *` (so npm accepts it), but it is built against react-native 0.84 and this app is on 0.88.1 / SDK 58; whether it compiles and runs there is only known after the first dev build.
```bash
# on a machine with Android Studio or Xcode (not part of this slice's evidence):
SUPABASE_URL=... SUPABASE_PUBLISHABLE_KEY=... npx expo run:android   # or run:ios; or an EAS development profile
```
- **Still missing for a real sensor:** (1) a dev build installed on a real phone, (2) a sensor flashed with firmware 4.F2b with the setup flow switched on and a per-unit security-2 salt + verifier in NVS (none exists today, `firmware/DEV_GUIDE.md`), (3) the SRP user name: the app uses `wifiprov` (ESP-IDF default, `NW_SRP_USERNAME`), **UNVERIFIED and not in the contract**; the factory tool must derive the verifier with the same name, (4) the real `PlantSetupService` and photo/QR (`expo-image-picker`, camera): in a real build these two steps still use the in-memory fakes, so plant details and the photo are NOT saved, (5) a deployed `claim-token` / `device-claim` on the project plus RLS-visible `devices` row (`hw_id` match uses the 6 hex of the advertised name because `connect()` only gets the name; carrying the full `hw_id` through the interface is a possible follow-up), (6) signal strength (the library gives none, the list shows 2 bars). Because the library cannot split prov-config from apply, `nw-claim` is sent before the apply call (same effect as the contract order). **Test 5.5 (real phone, iOS and Android, wrong secret refused after 5 tries) is NOT done; 4.A3 is not Done.**
- The in-app timer and the 3-minute target are shown, but setup time on a real sensor is measured in 5.5, not here. **4.A3 is Done only after test 5.5 on a real phone** (PR #56 C4); the green Jest/web run here is not that test.
- Wi-Fi password rule (PR #56 C2): `validateWifiPassword` accepts 8-63 characters (WPA2), empty only for open networks (the UI skips the field there).

Requirements: FR-A06 (list with status chips dry / wet / low battery / offline, detail with latest values and 7-day hourly chart), FR-A02 (no device cap), FR-A08 + A-022 (remove plant with warning and typed confirmation, then keep or release the sensor), NFR-06.

## 4.A4 slice 2: gallery, export before delete, hourly table (mock only)
Requirements: FR-A05 (unlimited dated photos, newest or oldest first), FR-A04 (location type, room, soil type shown on detail and gallery), FR-A06 (hourly table, 168 rows), FR-D02 (24 reports a day = 24 rows with a value), FR-A06 and the readings_hourly design (a missing hour is a gap, no row), FR-A08 + A-022 + NFR-07 (export before delete; photo objects removed from storage).
- **Hourly table** (`src/ui/HourlyTable.tsx`, grid in `src/plants/hourly.ts`): columns are the readings_hourly fields of the contract (moisture_avg, temp_avg, rh_avg, lux_avg, vbat_min_mv), newest first, a missing hour is a dash. The service always returns the 168-hour grid (`hourlyGrid`). Boundary tests in `src/__tests__/hourly.test.ts` (empty, one reading, 24 readings, gap in time, window edges) and in `plantsSlice2.test.tsx`.
- **Gallery** (`src/screens/PlantGalleryScreen.tsx`): every photo of the plant is rendered (no cap, no windowed list). Mock photos have no image bytes, so tiles show the date only.
- **Export before delete** (`src/export/exportGate.ts`, `RemovePlantScreen`): the delete button stays disabled until `exportData` succeeded AND the exact name is typed. The export is account-wide because GET /export has no plant_id. The export result is metadata only (file name, counts); in a real build the file is handed over before it resolves (4.A9, see the GET /export bullet above).
- **Photo objects** (C2 gate from PR #65): after `delete_plant`, the app calls `removePhotoObjects` with the returned paths; a failure keeps the paths on the Removed screen with a retry.
- **Not in this slice:** account delete gate (DeleteAccountScreen is 4.A2), upload ("+ Add"), full-screen photo, long-press delete, real Supabase `PlantsService` (still mock only, never run against a backend).
