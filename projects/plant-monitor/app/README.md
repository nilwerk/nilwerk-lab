# Plant Monitor app (tasks 4.A2 account and profile, 4.A3 device setup UI, 4.A4 slices 1 and 2 plants)

Expo (SDK 58) + TypeScript (strict). Screens: Welcome S01, Sign up / Sign in S02, Profile S03, Delete account S04, Premium sheet S40, plus (4.A4 slice 1) Plant list S20, Plant detail S21 (with hourly table S22 and metadata), Photo gallery S23, Remove plant S24b/S24c with export first, a Plants/Profile tab bar
(wireframes: `wireframes/index.html`). Requirements: FR-A01 (account), FR-P04 (plan mirrors `profiles.is_premium`), NFR-06 (own rows only, RLS), NFR-07 (delete removes all data, export first).
Brand: the aligned set approved in A-040 (`theme.ts`, `tokens.json`, `assets/` copied from `showcase/brand/app/`; regenerate there, not here). English only, strings in `strings/en.json` (A-024).

## Run
```bash
npm ci
npm run typecheck && npm test                      # typecheck + 261 unit/screen tests (no backend needed)
EXPO_PUBLIC_MOCK_AUTH=1 npx expo start --web       # whole app against an in-memory mock of Supabase (no account, no network)
```
Real backend (needs a Supabase project, Arsany's step, see `../cloud/README.md`): set these environment variables before `expo start` / EAS build. Names only, values are never committed:

| Name | What |
|---|---|
| `SUPABASE_URL` | project URL (https) |
| `SUPABASE_PUBLISHABLE_KEY` | the NEW publishable key (`sb_publishable_...`), public by design; never a secret / service-role key |
| `CONTACT_EMAIL` | address behind "Contact us" on the Premium sheet. Default `nilwerk.team@gmail.com` (A-048, the one shared mailbox for now); set another value to override, set it to an empty string to hide the link. Opens `mailto:` with subject "Plant Monitor – Premium activation" |

`app.config.ts` copies them into `extra`; `src/config.ts` reads them. Without them the app shows a "not connected to a server" message instead of crashing.

## Device setup flow (4.A3 UI + 4.A3b slice 1 real BLE code, no hardware run)
Profile -> "Add a sensor" -> S10 find sensor, S11 connect (type the label code), S12 Wi-Fi, S13 name and link (+ S13e error states), S14 photo, S15 plant details, S16 done with the setup timer (target 3 min, NFR-03). Requirements: FR-A03, FR-D03, FR-A04, FR-A05, FR-A02 (add another). **No hub pairing step: the Raspberry Pi hub and screen S17 are v1.1, not v1 (A-023).** Plant removal / release (A-022) is separate.
- The screens only talk to `src/provisioning/types.ts` (`ProvisioningService`, `PlantSetupService`, `PhotoSource`), mirroring `docs/interfaces/ble-provisioning.md` and `openapi.yaml` (`/claim-token`, `/device-claim`). `fakeProvisioning.ts` implements it in memory (5 wrong codes close setup mode, wifi_failed / device_owned / claim failures) and runs the whole flow in tests and in the mock web build (`EXPO_PUBLIC_MOCK_AUTH=1`). Pure state machine: `src/screens/setup/setupState.ts`.
- **4.A3b slice 1 (real BLE, built, NOT run on any hardware):** `src/provisioning/bleProvisioning.ts` implements `ProvisioningService` for real: scan for `NW-xxxxxx` (name prefix + service UUID `b53672dd-5227-40a0-8b6f-6f836f8a584c` where the platform reports it), security-2 connect with the label secret, Wi-Fi scan, `POST /claim-token` -> `nw-claim` -> prov-config/apply -> (after a successful apply: no more BLE requests; a refused apply reads `nw-status`) -> confirm the devices row under RLS (checked once a second for up to 90 s, `maxLinkMs`; not confirmed = `link_lost`), and maps every outcome to the existing setup error states (the 5-wrong-secrets cut-off is the device's: the app only reports `wrong_code`, or `setup_closed` once the sensor stops advertising). All Bluetooth goes through `bleAdapter.ts`; `espAdapter.ts` is the glue to `@orbital-systems/react-native-esp-idf-provisioning` **0.7.1** (exact pin, loaded lazily); `claimApi.ts` is the cloud side. `App.tsx` uses it when the build is not mock, Supabase is configured and the platform is not web; otherwise the mock or "not available" path is unchanged. Tests (mocked adapter / library / fetch, with error paths) are in `src/__tests__/bleProvisioning.test.ts` and `espAdapter.test.ts`.
- **Dev build (needed for BLE, Expo Go cannot do it):** `package.json` has `expo-dev-client` (~58.0.21, the version `expo install` picks for SDK 58) and the BLE library; `app.config.ts` has both config plugins (BLE only, `neverForLocation`). `npx expo prebuild --no-install` was run on a scratch copy and produced the expected Android permissions (BLUETOOTH_SCAN with neverForLocation, BLUETOOTH_CONNECT, location capped at API 30) and iOS `NSBluetoothAlwaysUsageDescription`. **Not run:** the native compile (`expo run:android` / EAS), because no Android SDK / Xcode / EAS account here. **UNVERIFIED:** the library's peer dependencies are `expo/react/react-native: *` (so npm accepts it), but it is built against react-native 0.84 and this app is on 0.88.1 / SDK 58; whether it compiles and runs there is only known after the first dev build.

```bash
SUPABASE_URL=... SUPABASE_PUBLISHABLE_KEY=... npx expo run:android   # or run:ios; or an EAS development profile
```
- **Still missing for a real sensor:** (1) a dev build installed on a real phone, (2) a sensor flashed with firmware 4.F2b with the setup flow switched on and a per-unit security-2 salt + verifier in NVS (none exists today, `firmware/DEV_GUIDE.md`), (3) the SRP user name: the app uses `wifiprov` (ESP-IDF default, `NW_SRP_USERNAME`), **UNVERIFIED and not in the contract** (Theo owns the contract follow-up for the SRP user name and the wording, review of PR #126, C1/C2; this PR does not edit `docs/interfaces/ble-provisioning.md`); the factory tool must derive the verifier with the same name, (4) the real `PlantSetupService` and photo/QR (`expo-image-picker`, camera): in a real build these two steps still use the in-memory fakes, so plant details and the photo are NOT saved, (5) re-setup of a sensor the user already owns (review C3, fixed here): the "claimed" confirmation accepts only a `devices` row whose `claimed_at` is not before the token issue time, taken from the server (`expires_at` minus 15 min of the `/claim-token` response, so phone clock skew is irrelevant); if `expires_at` is unusable the phone clock minus 2 min is used (documented in `claimApi.ts`; UNVERIFIED against the real server, covered by unit tests only, incl. a stale-row test), and a deployed `claim-token` / `device-claim` on the project plus RLS-visible `devices` row (`hw_id` match uses the 6 hex of the advertised name because `connect()` only gets the name; carrying the full `hw_id` through the interface is a possible follow-up), (6) signal strength (the library gives none, the list shows 2 bars). - **Photos into the export archive (4.A9b, NFR-07, FR-A01, FR-A05; owner decision A-107 option b):** the JSON export only links the photos (signed Storage URLs, valid 7 days). `src/export/photoExport.ts` downloads every photo behind those URLs, `src/export/zip.ts` (own stored-ZIP writer, no new dependency) packs `export.json` (untouched bytes) + `photos/*` into ONE `plant-monitor-export-<date>.zip`, and only then does the file hand-off run. **Delete stays blocked until that whole archive is saved:** `ExportResult.complete` is true only for a JSON export whose photos were all saved and handed over; both delete screens gate on it. All-or-nothing: if any photo fails, nothing is handed over and the screen says how many photos failed (`export.photos.failed`), that nothing was saved to the device and that delete is locked; the same export button retries (it fetches fresh links). Expired links (date in `expires_at`, or Storage answering 400/401/403) get their own message (`export.photos.expired`). **Host check:** a photo URL is fetched only if it is https (http only for a localhost dev backend), has exactly the host of the configured Supabase URL, no credentials, and a `/storage/v1/object/sign/plant-photos/` path; anything else is rejected without a request (`export.photos.rejected`), redirects are refused, no Authorization header is sent. **CSV** is still handed over but never counts as complete (it lists photos, does not contain them) and does not unlock delete. **Contract:** `docs/interfaces/openapi.yaml` /export says `photos:[{plant_id, taken_at, url}]` [proposed]; PR #130 (4.B2c, not merged when this was written) adds `id`, absolute `expires_at`, `file` and `url: null` for a missing object. The client needs only `url`; the extras are optional. A photo with `url: null` has no file in Storage, so it is reported ("N photo(s) ... could not be included") and does not block delete as long as at least one photo was saved or the list is empty (see round 2 below; decision for Arsany in the PR). Tests: `photoExport`, `zip` (also checked by python `zipfile`), `realPlants` (real caller path), `deleteAccountPhotos` (screen + real service + fake fetch), plus mutation runs in `showcase/items/2026-11-18_4.A9b/mutation-output.txt`. **Review round 2 (Theo C1-C3):** (C1) every photo-failure message now says what reached the device: nothing was saved and delete stays locked (no "your data arrived"); a non-photo error (archive too large / out of memory) is its own code `photos_archive` with its own text, not "0 of N photos failed". (C2) **`url: null` rule:** a photo with `url: null` is "missing, not blocking" ONLY when at least one photo was saved or the photo list is empty; if the list has photos and none was saved (`saved === 0`, `total > 0`) the export FAILS (`photos_none`), nothing is handed over and delete stays locked. Still open for Sana in #130: confirm `null` follows only a per-item "not found", never a transient signing error; Arsany to acknowledge the rule (A-107 follow-up). (Size cap) the summed `Content-Length` of the photos is checked before each body is read (150 MB total, `MAX_PHOTO_BYTES`); over it the export fails with `photos_too_large` ("too large for the in-app export"), nothing handed over. The photo URL path is pinned to `/storage/v1/object/sign/plant-photos/`. **Follow-ups (not in this PR):** a streaming ZIP writer (the archive is still built in memory, about 2x the photo bytes, so the cap is conservative and unmeasured on real phones); removing one plant still downloads every photo of the account; a custom Supabase domain would need its signed-URL host allowed; after #130 is deployed, drop the stale "no edge function exists" header in `exportClient.ts`. **Contract wording:** `openapi.yaml` `/plants/{id}` and `/account` now say a CSV export alone cannot satisfy the delete gate (needs ADR or Q-ID note from Theo).
  **Unverified:** not run on a phone; not run against the real backend (export function not deployed); the in-memory archive and the 150 MB cap are not measured on a device; `redirect: 'error'` is honoured by browsers but React Native's fetch may ignore it (the final URL is also checked when the platform reports it).
- Delete error wording is honest on purpose: the function releases devices and deletes photos before the auth user, so a 5xx or a dropped connection can leave data partly gone. A 401 after such an error is shown as "may already be deleted, sign in again to check", not "session expired".
- Apple/Google sign-in and store assets are later tasks. The BLE dev-build configuration exists (4.A3b slice 1) but no dev build has been made.
